Act I sets the rules of the game. Five slides on what we deliberately constrained ourselves to, because every architectural decision downstream falls out of these constraints.

Slide 6. There are two tempting wrong answers to "we want a modern admin experience": reskin wp-admin with CSS overrides, or fork WordPress and ship our own shell. Both are traps. The reskin war is the trap people fall into first. You inspect a wp-admin page, override a few selectors, and ship. Then the next WordPress release renames a class. Then a plugin injects its own notice with !important. Then a different plugin's dashboard widget breaks because your override hit it too. You are now in a permanent maintenance war against an admin surface you do not control, fought in the worst language for the job (specificity), and you are losing. The fork looks like the way out. Write fewer lines, dodge the WordPress hook order, ignore the multisite split, ship a prettier dashboard in a week. You also inherit every plugin incompatibility, break every existing integration, and sign up to maintain a parallel admin shell forever. Forking is a tax that compounds. Studio takes a third path: take over the request from inside the WordPress admin lifecycle, render our own chrome, exit before wp-admin gets to render. We never fight CSS specificity because wp-admin's CSS never loads. We never fork core because we live inside its lifecycle. Plugins still work because WordPress still boots normally. The escape hatch matters: a super admin who needs the old shell can flip ?mc_studio=off and the cookie sticks for the session. StudioGate stands aside without complaint. We never paint ourselves into a corner.

Slide 6a — Before vs. after, the layout. Left column is the path you take when you decide to "just take over the admin page" without thinking about the lifecycle. You hook admin_head, you ob_start, you let wp-admin render into a buffer, you regex out the chrome you don't want, you inject your own, you echo the result. Notice the orphan ?> tags, the stray closing brace where the add_action call was missing its closing paren, the allow-list filter on script_loader_src — every one of those is a real anti-pattern from real WordPress plugins. It works once. Then core changes a wrapper id, your regex misses, a div leaks. Then a plugin enqueues a script late, the buffer captures half of it, the page breaks for that user only. Then someone files a bug that only reproduces with H5P + LTI + a specific browser. The asset story is the other half: because you're not inside the normal lifecycle you end up filtering script_loader_src by hand to decide which plugins get to load. Right column is what we actually wrote: 56 lines of Blade, doctype to closing body, with wp_head() and wp_footer() doing the work. Every plugin in the ecosystem (H5P, LTI 1.3, CAS/SAML) registers its assets through admin_enqueue_scripts the normal way, and those two hooks deliver them. No regex, no buffer, no allow-list. The chrome is a single file with a clear contract. The skip link is the first focusable element (WCAG 2.4.1 Bypass Blocks). The main has tabindex=-1 so the skip target can receive focus. The lang attribute is bound so screen readers pronounce content correctly. The robots meta is noindex on the rendered page because this is admin chrome. Next slide unpacks what those two hooks actually carry and why this shape gives us zero per-page chrome drift across every Studio screen.

Slide 6b — The payoff. This is the analysis side. Two hooks: wp_head and wp_footer. Between them they carry every script and stylesheet that any plugin in the ecosystem will ever ship through the WordPress admin lifecycle. We don't have to know what those plugins are. We don't have to update the layout when a new one ships. The contract is wp_head and wp_footer, forever. The screen mount contract is the other half. The chrome is owned by layout.blade.php and nothing else. The topbar partial is included exactly once, by the layout. The sidebar partial is included exactly once, by the layout. Screen views are leaves — they render the body of their page into the studio-main host. They never re-emit doctype, never re-emit the shell, never reach up and modify the chrome. This is what makes "add a new screen" a one-file operation. The file goes under resources/views/studio/screens/, the StudioRouter registers it, the sidebar links to it, and the layout mounts it. The new screen author cannot break the topbar even if they try, because they never see it. They cannot drift the sidebar because they don't own it. Compare that to the left-hand path on the previous slide: in that world every screen author has to remember to inject the chrome correctly, has to know the regex rules, has to trust the buffer. Here they only have to write the body. Single-source chrome, zero per-page drift, and "add a screen" is a one-file pull request.

Slide 7 — Three CPTs, not two. This is the first architectural decision and it predates everything else in the deck. Forking Pressbooks gave us the book CPT model: Book → Part → Chapter. Two levels of structural nesting under the container. We tried for about a week to map microcredentials onto that, and it failed in both directions. For occupational MCs — short, skills-aligned, "Forklift safety" or "Restaurant manager onboarding" — the part/chapter model is too expensive. A 90-minute MC has maybe 3 competencies and 12 learning moments. Mapping competency → part and moment → chapter gives you 3 TOC entries and the actual content is one click deeper than it should be. Mapping moment → chapter and ignoring parts gives you a flat 12-chapter dump with no grouping. For university MCs — "Intro to Data Ethics" running 8 weeks — the opposite happens. A week has multiple sessions, each session has multiple activities. Two levels means either weeks-as-parts and sessions-as-chapters (and activities collapse into the chapter body, which kills H5P/video/check granularity) or sessions-as-parts and activities-as-chapters (and the week-level rhythm disappears). Gagné's 9 events of instruction — the pedagogical model the authoring team designs against — needs one structural slot per event. You can't honor "gain attention → recall prior learning → present new material" if your structure tops out at "chapter." So we introduced Lesson as a third level — a structural slot between Module and Section. The Section is the leaf where the author writes the full learning experience (H5P, video, embeds, check blocks, the whole Lexical authoring surface). The Module is the container the learner enrolls in. The Lesson is the grouping that makes the tree shape match the pedagogy. A word on the editor story. Section gets the *full* Lexical — every block plugin, every embed type, the works. That's where the actual learning experience lives. But Module and Lesson also need *some* rich text: a module overview, a lesson description, a transition blurb between sections. For those, we don't want the full editor sitting in a 600-pixel surface intimidating an author who just wants to write two sentences in bold. So Module and Lesson — and any other "give me a paragraph with light formatting" field anywhere in Studio — use the same *minimal* Lexical instance: bold, italic, links, lists, and that's it. One editor build, two presets, used wherever the field demands it. This means a content author learns one editor and it adapts to context, instead of learning "the title editor," "the description editor," and "the section editor" as three separate UIs. The CPT slug 'mc_section' is a relic: it used to be 'mc_module' before we added Lessons, and we kept the slug stable to avoid a migration on every existing post. The Section.php docblock notes this. It's a small lie in the database that prevents a large headache in the upgrade path. This decision is upstream of Organize, upstream of the REST namespace split, upstream of the BEM blocks. The architecture in the rest of this deck is shaped by the choice to have three levels — and the choice was made because the content model demanded it, not because three felt more elegant than two.

Slide 7a — Before vs. after, the CPT query. Left column is real code from this repo, pre-refactor commit 3c388ac. We had a two-level model (Module + Section) joined by a postmeta key called _mc_unit_id — a holdover from when modules were called units. Every "show me this module's sections" was a WP_Query with a meta_query JOIN against wp_postmeta. Every save had to write the meta key. Every orphan had to be tracked with a separate Section::getUnassigned() helper. The ordering still used menu_order on the section itself, but the parent relationship lived in postmeta. That worked, but it had costs that compounded. The JOIN was a JOIN. Postmeta is a key/value table — you cannot foreign-key it, you cannot cascade-delete from it, and you cannot reorder rows of it without writing N updates and busting caches. Every new feature that wanted to know "which module owns this section" had to either re-implement the meta read or call a static helper. And any time a section ended up without a unit (a half-finished create, a botched migration, a plugin that forgot to set the meta), it disappeared from the tree silently — hence Section::getUnassigned() existing in the first place. Right column is the current code. Same function name, same return shape, completely different data path. The hierarchy is now real WordPress parent/child via post_parent — a native column that core indexes, that wp_delete_post cascades through, that wp_update_post treats as a first-class relationship. The within-level ordering is menu_order — the same native column nav menus and page hierarchies use. The two-level model became three-level (Module → Lesson → Section) and the query got simpler, not more complex, because every level uses the same primitive. The one-line guard — "if lessons is empty, return [] " — prevents a real bug: post_parent__in against an empty array would match every orphan section in the database, which is exactly what Section::getUnassigned() used to surface. The guard makes that impossible by construction. Section::getByUnit() and Section::getUnassigned() were both deleted in 3c388ac. No production data carried _mc_unit_id, so no migration was needed. The schema simplified, the query simplified, the helpers deleted themselves. Next slide unpacks why this matters operationally — what reorders, deletes, walks, and orphan-safety look like once you let the database do the hierarchy work for you.

Slide 7b — The payoff. This is the operational consequence of the previous slide. Each row in this table is a concrete thing the engineering team has to do — fetch, order, reorder, delete, walk, guard, helper-maintain — and each row got simpler in the move from postmeta to post_parent. The fetch row is the headline. Pre-refactor, every list query JOINed wp_postmeta to filter by _mc_unit_id. Post-refactor, post_parent is a column on wp_posts that core already indexes. No JOIN. The reorder row is where the cost compounded fastest in the old model. Drag-and-drop reordering means writing the new order for every sibling after the drop. In the postmeta world, that is N update_post_meta calls plus the cache busts that go with them. In the post_parent + menu_order world, it is N wp_update_post calls against a native column — same N writes, but they hit indexed rows and trigger the cache invalidation core already knows how to do. The cascade row is the one that would have bitten us hardest later. wp_delete_post will recursively delete children via post_parent for hierarchical post types. In the postmeta world we would have had to write that ourselves, find every section with _mc_unit_id matching the deleted module, delete them, then handle the lessons-don't-exist- yet case when we added the third level. In the current world, deleting a module deletes its lessons, which deletes their sections, without us writing a single recursive query. The orphan-safety row is the one I want to flag explicitly. The Section::getUnassigned() helper existed because postmeta lookups silently miss rows that don't have the key set. We needed a way to find sections that had been orphaned by a botched save. Post-refactor, the equivalent bug class is "what if I call getSections on a module with no lessons" — and the one-line guard makes that impossible. The defensive helper became a defensive line. The helpers-needed row is the final receipt. Section::getByUnit, Section::getUnassigned, and a couple of Module-side helpers were all deleted in 3c388ac. They existed only to paper over the postmeta model. They are not in the codebase anymore. That is the cleanest kind of refactor: the one where you delete more code than you write. The callout reframes the whole sequence: we added a third level to the hierarchy (Module → Lesson → Section) and the data layer got simpler at the same time. That is unusual. It is unusual because the simplification was not from "add a level"; it was from "stop putting hierarchies in postmeta." Adding the level was the pedagogical reason to refactor; moving to post_parent was the engineering reason. They happened in the same patch series, and the result is fewer queries, fewer helpers, fewer defensive guards, and a deeper tree.

Slide 7. Twelve classes. Each one fits in a single screen. None of them know about more than two collaborators. You can read the whole namespace top-to-bottom in 20 minutes and have the full mental model. This is deliberate. The temptation in an admin shell is to grow one god-class — `StudioManager`, say — that knows about menus, assets, gates, and routing. We didn't. The cost is a few more files; the benefit is that each file is testable in isolation. Look at the test count: 88 unit tests, many of which mock exactly one collaborator per class.

Slide 8. This is the whole boot sequence. Read it priority by priority: - admin_init@1: caps migration (version-gated, cheap when no-op) - init@5: register the 5 default Studio screens - init@6: register sidebar items — has to come after the router so the menu has something to point at - admin_menu@10: register hidden submenu pages so WP recognises the slugs - admin_init@2: classic-mode cookie router — has to run before the gate - admin_init@5: the gate itself — decides to take over or stand aside - pressbooks_blade_directives: register @canEditMc / @canUseStudio - admin_enqueue_scripts: enqueue the bundle, gated internally If you don't understand why a priority is what it is, the file's PHPDoc explains it. Slide 9. The chrome is one Blade layout: layout.blade.php. Every screen renders inside that one main element. The screen view owns its own h1 and its own inner layout, but it never touches the chrome. The screenshot on the right shows the Course context — notice Organize and Settings are visible because we're inside a specific microcredential. Slide 10a — MenuFactory. The Pressbooks codebase historically modeled every admin menu item as a subclass of MenuItem. The constructor of each subclass set the slug, title, icon, capability, contexts. Six items meant six classes meant six files meant about 150 lines of constructor boilerplate that did nothing except assign properties. The MenuItem::make() fluent factory replaces that entire pattern. The value object is immutable after register(); the registry is a single container singleton; visibility per surface is a method chain, not a class hierarchy. The "Studio eligible" flag is a separate concern from the wp-admin context list because some items appear in both shells and some only in Studio — modeling that with subclasses would have needed a matrix of mixin traits. With the fluent factory it's one method call. The non-obvious win is testability. Testing the legacy pattern meant instantiating each MenuItem subclass and inspecting its protected state. Testing the new pattern means calling MenuItem::make() with a controlled set of args and asserting the resulting value object's public getters. The test reads like the production code, because production code is one expression. This is the Phase-D-era refactor that quietly enables every future menu item — including the hidden screens pattern, where we register the router entry but skip the menu item entirely. With subclasses, "don't register a menu item" meant deleting the class. With the factory, it means not calling make(). One less thing to remember.

Act II is the meat: how the architecture actually works. Eight slides, mostly code, mostly real source from the branch.

Slide 11. This is the kebab menu you see open in the screenshot. 92 lines of Blade. Three callers: the module card, the lesson card, the section row. Each caller passes $id, $ariaLabel, and an $items array. That's it. The accessibility plumbing — aria-haspopup, aria-expanded, aria-controls, role="menu", keyboard handlers — lives in this one file. Fix a bug here and you fix it for all three rows. The Alpine state machine (mcKebab) lives elsewhere, again shared. This is what "Blade as a first-class citizen" buys us: a real templating language with includes, props, and conditionals, not string concatenation in PHP.

Slide 12. Three directives. They compile to native PHP if statements — there's no runtime overhead beyond the cap check itself. Templates read like English: "if the user can edit this microcredential, show the edit button." The alternative — calling Permissions::canEditMc($id) inline with raw PHP tags — works but reads poorly and tempts people to skip the cap check "just for now." A directive makes the right thing the easy thing. When we add a new cap, we add a directive here in one line, and every template that needs it can use it the next day. No refactor.

Slide 13. This is the single most important architectural decision in the branch. The naive design has two row templates: one in PHP for initial render, one in JS for client-side appends after a REST create. They drift. They always drift. One of them gets a class added that the other doesn't, and the bug shows up three weeks later when a user creates a module and the icon is missing. The fix is to never have two templates. shapeModuleRow returns the same shape whether it's called from the initial-render view model or from the REST create handler. The Blade partial that renders a module card is the same partial both times. The HTML the user sees after creating a module is byte-identical to what they would have seen if they'd reloaded the page. That's the contract. We pay for this with a slightly larger view model. We get back: zero template drift, zero "looks different after create" bugs, and a much shorter client-side script — organize.js doesn't know what a module row looks like.

Slide 14. This is the slide that sells the whole architecture to people who don't care about hooks. Show them the dashboard. Ask what's different. They'll say "it's cleaner." That cleanliness is the product of one decision: Studio owns the document. We didn't write a hundred remove_action calls to hide notices. We never gave them a place to render. The layout.blade.php template starts with <!doctype html>, ends with </html>, and the admin bar simply has nowhere to attach. wp_head and wp_footer still fire so JS and CSS from H5P / LTI / SSO still load — they just don't get to paint chrome. Phase 2 question: super admins still need to see critical notices somewhere. The plan is a Studio inbox that subscribes to admin_notices on a filtered list (security, billing, plugin updates) and surfaces them in the topbar with a badge count. Regular users don't see the inbox.

Slide 16. Two scales, two namespaces: - --pb-* are the design-system primitives, lifted verbatim from the prototype at docs/microcredentials-exploration/project/styles.css. They live in studio/tokens/colors.css and will eventually lift out into a tokens stylesheet shared across the whole Pressbooks surface. - --studio-* are chrome semantics (surface, border, brand-on) split across studio/tokens/*.css by category. The rule for component CSS: never inline a hex code. If you find yourself typing #6ba3ad, you're skipping the token. Add one if it doesn't exist (in the right tokens file); don't bypass the system. This is what makes a theme swap a 10-line CSS diff instead of a search-and-replace nightmare.

Slide 16b — From stylesheet to design system. Until recently, all Studio CSS lived in one file: studio.css, ~2,700 lines, section-commented. It worked, but every new rule's home was a judgment call ("which section comment is closest?"), and the file got harder to navigate as it grew. We split it into five layers — tokens, base, components, layout, screens — each with its own directory under studio/. The original studio.css is now a one-line forwarder that @imports studio/_index.css, which in turn @imports every layer in the right order. Vite still inlines all of it into one CSS bundle at build time, so the runtime cost is identical. What we gained: 1. The decision tree above is now codified in _index.css's header comment. "Where does this rule go?" has a single answer, not a judgment call. 2. Load order is enforced by the index file, not by section ordering within a single document. Tokens always come first; screens always come last so they can override component defaults inside their scope. 3. A screen file is small enough to read in one sitting (organize.css is ~487 lines vs. its old section comprising ~600 lines mixed with everyone else's rules). 4. Splitting surfaced ~180 lines of dead CSS — rules whose selectors no longer matched anything in the Blade views. Audited and dropped. What didn't change: the naming convention (BEM, .studio-* for chrome, .mc-* for features), the no-Tailwind rule, the no-utility-classes rule, the one-Vite-entry rule. All of those still hold; we just gave the rules a better filing cabinet.

Slide 19 — An iterative design system that evolves naturally. For the audience members who care about design systems specifically: this is what you need to hear. We have not shipped a design system. We have shipped the four layers a design system is built on, in the right relationship to each other. Tokens are the bottom layer. Every colour, every space increment, every radius, every shadow is a CSS custom property. The components reference the tokens, not literal values. The day someone wants a dark mode or a white-label tenant theme, they override the tokens at the :root level and every component inherits. No component code changes. Components are the second layer. BEM blocks are doing the job that "design system components" do in a React ecosystem — self-contained, named, reusable, no accidental cross-block coupling. The difference is that our components are HTML+CSS, not JSX+TypeScript, so they're portable to any rendering technology that can emit a tag with a class. Behavior is the third layer. Where a React design system would ship <Combobox> as a TSX component with hooks, we ship a Blade partial (mc-combobox) plus an Alpine factory (mcCombobox) plus a BEM block. The pattern is the same — markup, behavior, styles co-located by naming — but without the framework lock-in. A future combobox, popover, toast, or command palette uses the same shape. We don't have to invent a new pattern for each. Theming is the fourth layer. Because every visual property is a token, swapping themes is overriding tokens — not forking components. This is the thing that breaks in most design systems built without this discipline up front: by the time you want dark mode, half your components have hardcoded colour and you're doing a six-month migration. What we have NOT done yet, and should be honest about: there's no Storybook, no published token package, no versioning story, no contribution guide. Those are all on the next-up list. But the foundation is sound enough that adding them is documentation and packaging work — not a rewrite. The 30th component will look like the 3rd because the patterns are already there. The closing line is the one to remember: the hard part of a design system isn't the components, it's the discipline of naming, tokenizing, and resisting the framework-of-the-month. We paid that cost while building Organize. Future components inherit it for free.

Slide 19a — One system, three surfaces (part 1: the duplication). This is the "sell the reuse" slide, part one. The previous slide made the architectural case that we have the foundations of a design system. This slide shows where those foundations pay off: the moment we point them at a second surface, and we have two such surfaces already on the roadmap — the learner theme and the Lexical editor. Open with the duplication that exists today. The mc-learner theme has its own --mc-color-primary, --mc-space-md, --mc-radius-md, --mc-text-base. Studio has --pb-* and --studio-* equivalents. Same concepts, defined twice, drifting independently. That drift is exactly the failure mode a real design system prevents. The fix is not "rewrite the theme to look like Studio." The fix is extract the tokens into a shared package — @pressbooks/design-tokens or equivalent — and have both surfaces consume it. The theme's brand colours become a token override at :root, not a hardcoded value. The Studio chrome and the learner reading surface stay visually consistent without anyone having to manually keep them in sync. Lexical is the second beneficiary. When we ship the new editor, its node styling — paragraph spacing, heading scale, code block radius, selection colour, focus ring — all need to come from somewhere. The honest options are: (a) invent a third token set just for the editor, or (b) reuse what we already have. Option (b) is free if the tokens are in a shared package; option (a) is six months of drift waiting to happen. The callout is the takeaway for this slide: this isn't hypothetical. The duplication is in themes/mc-learner/assets/src/styles/theme.css lines 1 through 44 right now. The next slide covers what we unlock by closing that gap.

Slide 19b — One system, three surfaces (part 2: the payoff). This is the business-case half. The previous slide showed the duplication and named the fix (shared token package). This slide names what the audience gets in return. Brand consistency end-to-end is the one to lead with for any non-engineering listener. Today, an author writing in Studio sees one set of colours, spacings, and type; a learner reading the same content sees a different set; the editor inside Studio will be a third set if we don't do this work. Unified tokens collapse those three into one visual story. White-label is the commercial argument. Pressbooks has tenants who want their own brand. Today that's a theme fork or a stylesheet override. With unified tokens, it's "set --mc-color-primary to #yourcolour at :root" and every surface picks it up. Same for dark mode, high-contrast, accessibility themes. Lexical is the engineering argument. The new editor is coming. If we don't unify first, we will invent a third token set for editor node styles and immediately start drifting. If we unify first, the editor inherits the system for free and stays in sync forever. The "next surface gets cheaper" line is the long-term argument. Every new surface we add — mobile, email, PDF export, embedded widgets — either starts from the shared tokens (cheap) or invents its own (expensive, drifts). The investment compounds. Closing line: the 30th component on the 4th surface looks like the 3rd component on the 1st surface. That is the definition of a real design system — not a Storybook, but a compounding investment.

Slide 21. This is the entire client-side architecture for create. The factory function returns an Alpine data object; createRow is the shared backbone that createModule, createLesson, and createSection all call. There is no Vue, no React, no JSX, no build-time component compilation. There is a function that returns an object with methods, and Alpine wires it to the DOM via x-data="mcOrganize". What's clever: the Accept: text/html header. The server returns a Blade partial; the client does insertAdjacentHTML. No client-side template, no string concatenation, no drift. The new row is real DOM that Alpine has already wired by the next tick. Mental model: the DOM is the source of truth. Alpine is the local interactivity layer. The server still renders. We don't have a Single Page App; we have a tiny enhancement layer on top of server-rendered HTML. This scales down better than React for a CRUD admin.

Slide 18. Two things to notice. First: the route registration is right next to the controller method. No config files, no DI magic. You read the controller, you see the route, you see the callback, you see the permission check. The wizard search you see in the screenshot is hitting SkillsController which sits in the same namespace. Second: every permission_callback is a real method. Never __return_true. Never even __return_logged_in. We have one controller-level gate (canEditMc on the subsite), and then per-row checks (current_user_can edit_post on the specific module) inside the handlers where the per-row identity is known. Two layers. Both checked. Both tested. The handlers also return structured WP_Errors with mc_-prefixed codes (mc_forbidden, mc_not_found, mc_invalid_position, mc_save_failed, mc_cascade_failed). The client matches on the code, never on the message, so we can translate the message without breaking the client.

Slide 18a — Skills API. Skills are the spine of the microcredential model. A microcredential declares what skills it confers; lessons declare which skills they practice; sections (eventually) tag the moments where a specific skill is exercised. Three different UI surfaces consume the same underlying skills library — and we built it so they consume the SAME api, not three parallel ones. The wizard is the first consumer: when an author scopes a new MC, the "What skills will this confer?" step uses GET /mc/v1/skills?search= with a debounced typeahead. Results are paginated chips, filterable by framework (O*NET, EMSI, institutional). The chip component is a Blade partial; the data shape is what SkillSerializer::toArray emits. Organize is the second consumer: each lesson row has a skills cluster with a "+ Add skill" button. Click it, the same chip-picker opens (same component, same data), the author selects, we POST to PUT /mc/v1/organize/lessons/{id}/skills with the full desired set. The endpoint is transactional — all skills are valid, or none are persisted, and the response includes structured error codes the client matches on. The edit screens are the third consumer, shipping next. The section editor will surface skills in a dedicated **Skills** configuration tab alongside the Lexical authoring surface — not inside it. Same chip component. Same API. Same JSON shape. No "edit-mode skill model" that diverges from the "organize-mode skill model." The discipline that makes this work is putting the seam at the repository, not the controller. SkillsRepositoryInterface defines find, search, byFramework. The default implementation talks to our skills table. A future O*NET-only provider, or a custom institutional taxonomy, plugs in as a different repository binding in the container. None of the controllers — wizard, organize, future editor — change. This is the architectural answer to "we'll need this in three places." Don't build it three times. Build it once, behind an interface, and let the consumers compose.

Slide 19. The cleverest 30 lines on the branch. The Organize screen wants HTML so it can insertAdjacentHTML. A future third-party API consumer might want JSON. Same endpoint, same handler, same shape — the responder branches on Accept. The hack: WordPress's REST server JSON-encodes everything it sends. If we just return HTML in a WP_REST_Response, the quotes get backslash-escaped into JSON garbage. So we hook rest_pre_serve_request, detect our text/html content-type, echo the raw HTML, and short-circuit the serializer. The filter is self-removing so it only affects this one response. This is the kind of "one small clever thing" that eliminates a whole class of bugs. The alternative — duplicating row templates in JS — would have saved us 30 lines here and cost us 200 lines of JS plus permanent drift. Worth it.

Slide 20. The Settings entry in the sidebar is visible in this screenshot because this user can manage settings. A user without the cap doesn't see the sidebar item AND can't reach the route — same cap, two enforcement points. The two-layer model matters. Reorder is a structural operation on the whole microcredential, so it only needs the subsite-level canEditMc. But rename and delete touch a specific post, so they additionally call current_user_can('edit_post', $id). The right grain at the right layer. The version constant is the safest way to add caps over time. Bump the version, add the new cap to StudioCapabilities::all(), and the Activation::grantStudioCaps routine re-runs on the next admin request for each site. Cheap when no-op (early-exit on version match), correct when the version differs. No migration scripts, no manual intervention.

Act III: how we got accessibility right without an accessibility consultant on retainer. Five slides on landmarks, live regions, keyboard DnD, focus, and contrast.

Slide 22. A screen reader hitting Tab on this page lands on the skip link first. That's WCAG 2.4.1 Bypass Blocks. Hit Enter, focus jumps past the chrome into <main id="studio-content" tabindex="-1">. The tabindex=-1 makes the main element programmatically focusable so the skip target actually works. One landmark per role. No nested mains. The h1 belongs to the screen, not the chrome — so a screen-reader user hitting H1 navigation lands on "Organize" or "Dashboard", not on the page title. This isn't accessibility theater. It's the document outline that screen readers expect, and it costs us nothing because we own the document.

Slide 23. Accessibility isn't a checklist we bolt on at the end. It's a load- bearing design constraint that shaped the components. Every interactive element in Studio is a real focusable button or native control with the right ARIA — not a styled div pretending to be interactive. The kebab menu is a real disclosure widget with aria-expanded and roving tabindex. The modal traps focus and announces itself with role=dialog + aria-labelledby. The drag handle is a focusable button you can operate with the keyboard. Form fields use native labels and aria-errormessage. Skip link is the first thing in the tab order. None of this is unusual — it's the WCAG-2.1-AA baseline we committed to in AGENTS.md, applied consistently because the components were built once and reused everywhere. The aria-live region is the one place where a sprinkle-everywhere anti-pattern is genuinely tempting. The instinct is "every component that emits status needs its own region." That's wrong. Multiple live regions interrupt each other; screen readers serialize them in unpredictable orders; the user hears half a message before the next one cuts in. So Studio has exactly one region, owned by the mcOrganize Alpine root, written via x-text on a single statusMessage property. The keyboard-dnd directive calls announce(msg) — no descendant gets its own region. The single live region is not a substitute for component-level accessibility. Those two layers do different jobs. Component ARIA tells the screen reader what each control IS and what STATE it's in (the kebab is collapsed, the dialog is open, the field is invalid). The live region tells the screen reader what just HAPPENED in a way they can't otherwise perceive (you picked up a lesson, the delete failed, your keyboard sort landed at position 3). The discipline question is what to announce. Mouse drag success? No — the user saw the row move. Mouse drag failure? Yes. Keyboard drag? Yes for everything — pickup, every move, drop, cross-parent — because the user can't see the change without it. This is the kind of decision that doesn't show up in a screenshot. It shows up when you put on a screen reader and try to reorder a lesson without a mouse. It works. That's the proof.

Slide 24. Two screenshots. Left: mouse drag mid-flight. Right: a cross-parent move of a section between two lessons. Both work the same way under the hood: focus a drag handle, hit Space to pick up, arrow keys to move, Space to drop, Escape to cancel. The implementation is one Alpine directive — mcKeyboardDnd — registered in studio.js, defined in directives/keyboard-dnd.js. No SortableJS, no react-dnd, no third-party drag library doing the keyboard work. We layer the WAI-ARIA Authoring Practices Guide keyboard pattern on top of the same DOM SortableJS already manages. Commits to cite: 18f868b promoted drag handles to focusable buttons. 262d837 added the directive itself. Together they shipped the keyboard story. The screenshot proves it works visually. The unit tests (we'll see them in the next act) prove it works programmatically.

Slide 24a — DnD poka-yoke. Poka-yoke is the Toyota Production System term for "mistake-proofing" — designing the affordance so that the wrong action is physically impossible, not just corrected after the user attempts it. The Studio DnD implementation has three layers of poka-yoke. Layer 1 — SortableJS group constraints. Each sortable list declares group: { name, put }. A lesson list will only accept items from groups matching its put list — sections from other lessons, never modules. The drag visualization itself shows no insertion line over an invalid target. The user cannot drop where they cannot see the line. Layer 2 — onMove guards. Even within a valid group, some positions are nonsense. The trailing "+ Add lesson" / "+ Add section" buttons are DOM children of the sortable container (so they reposition correctly when the list grows), but you cannot drop a lesson *after* the Add button. organize.js:361 rejects that position. Returning false cancels the drop and SortableJS automatically restores DOM state — no rollback code needed. Layer 3 — server validation. Even if a client bypassed both guards (modified JS, replayed an API call), the server validates the move: moveSection requires the target lesson to exist and be in the same MC, moveLesson requires the target module to exist. The REST endpoint returns 422 with a structured error code, the client rolls back the optimistic DOM change from its snapshot, and the live region announces the failure. Cross-parent moves deserve the call-out because they're the non-obvious feature. A section moving from Lesson A in Module 1 to Lesson B in Module 3 is a real workflow — the author realized the section belongs to a different topic. The server-side handler updates post_parent + menu_order atomically in one transaction. No "delete-then-create" dance. No orphaned skill assignments. The section keeps its ID, its history, its skill links. This is what "interaction at the level of the tree" means. The user doesn't think about modules vs. lessons vs. sections — they grab the thing and put it where it belongs. The system makes the invalid moves unreachable and absorbs the valid ones.

Slide 25. The screenshot shows the moment after a valid selection: button enabled, badge updated, screen-reader announcement fired. That coordination is trivial when the components share tokens — the disabled state isn't a different color, it's the same button with --pb-teal-50 swapped for a muted neutral via a single class. Focus rings: 4.7:1 contrast against the paper background. We measured. The teal palette was chosen partly because --pb-teal-70 hits AA against the off-white surface — the prototype's earlier red couldn't. Motion: every transition uses the same easing and duration tokens, so the shell feels coherent. One media query at the bottom of studio.css strips animations for users who've asked the OS to reduce motion. Two lines of CSS, big accessibility win.

Act IV: the parts that make this maintainable, not just shippable. Tests, design handoff, recipes for adding things, and the extensibility posture going forward.

Slide 27. This is a real test from the branch. Brain Monkey mocks WordPress functions; Mockery stands in for the view model; the controller runs unmodified. No bootstrap, no database, no HTTP — just the unit under test. The three-test minimum is the discipline: 1. Permission denied — request rejected at the controller gate. 2. Validation failure — bad payload returns the right WP_Error code. 3. Happy path — correct call returns 201 with the right shape. If a route doesn't have all three, it's not done. The reorder route adds a fourth (invalid positions); the cascade-delete route adds a fifth (child delete fails). The minimum is three; the ceiling is what the behavior demands. 88 unit tests, all running in under 5 seconds. The cost of writing them is real but small; the cost of NOT writing them shows up at 2am when a cap check regresses and an editor can delete someone else's module.

Slide 28a — Performance at scale. The performance story is not a feature we added; it's a property that falls out of the architecture. We never wrote a "make it fast for big courses" task. We never profiled and optimized hot paths. The architecture itself makes the slow path impossible to write. Initial paint is the biggest win. Most modern admin UIs ship as a SPA shell that boots, fetches JSON, renders a skeleton, then fills in. That's three round-trips and three paints before the user sees the tree. Studio sends one HTML document. The tree is in the markup. First paint is final paint. For a 2 000-section MC, that's the difference between a 200ms perceived load and a 2-second one. The tree query is the second win. OrganizeViewModel::get() does one WP_Query for all modules in the MC, then loads all lessons whose post_parent is in that set in a single query, then all sections the same way. Three queries total, all hitting the post_parent index. The naive implementation would be one query per parent — 50 + 400 + 2 000 = 2 450 queries. We pay 3. The DOM-as-truth model is the third win, and it's the load-bearing one for write performance. When you add a module, the server renders the exact Blade partial that initial paint used, returns it as text/html, and the client does insertAdjacentHTML. The new card is real DOM — Alpine wires it on the next tick. No client template duplicates the server template. No "edit" mode re-renders the whole tree. The most expensive thing the client does after first paint is move one <li> between two <ul>s. The "100 kebab menus" row is the subtle one. With Alpine, every row mounts an x-data root, but mcKebab is tiny (open/closed boolean, focus restoration). The kebab handler delegation is automatic via event bubbling on the page-level click listener that closes open menus. We never wrote "for large lists, virtualize" code. We just made each row cheap enough that 2 000 of them is fine. This is why "performance at scale" is one slide, not five. It's a property of the architecture, not a body of work.

Slide 28. The screenshot is the actual wizard, step 5, running on the branch. The prototype it was built from lives in the docs directory as a real HTML file you can open in a browser. The reviewer's job during PR is to open both and look for differences. Why this works: - The prototype is real HTML, not a Figma export. No "looks great in Figma, falls apart in code" surprises. - Claude can read both files, suggest the diff, generate first-pass Blade and CSS that hit 80% of the prototype. - Code Connect mappings (Figma's feature) link our .mc-* blocks back to Figma components so the next prototype update flows the other way too. The cost: discipline to keep the prototype directory accurate. The payoff: a designer can ship a wizard step in a day without writing JS.

Slide 29. This is the recipe. Not a tutorial — a recipe. It tells you the file you edit, in the order you edit them, and the commit boundary you ship at. Why six commits instead of one? Because each commit has a single reviewable concern. Reviewer can read commit 1 and know exactly what "new screen slug" means; doesn't need to wade through view-model code to verify a routing decision. The PR is a sequence of small, defensible changes. The doc at docs/studio/adding-a-screen.md walks the whole thing line by line. New contributor can ship a Studio screen in their first day without asking a single architecture question.

Slide 29a. The previous slide showed the manual recipe. This one shows the automation. The skill is a `.md` file the agent loads when the user says "build a new Studio screen from this prototype" — it then walks the agent through the same 6 commits, but enforces the design-system contract at every step. Why this matters beyond convenience: the skill encodes institutional memory. Every "we tried that, here's why it failed" lesson from Phase D — the anti-patterns we'll see in two slides — is now in a file the agent reads before writing a single line. New screens can't repeat the mistakes because the skill stops them at the gate. The two-phase split is the load-bearing piece. Phase A produces a static, fixture-driven view that the user can see in HMR within minutes. The approval gate is non-negotiable: no view model, no REST, no Alpine until the user signs off on the visual. Visual changes are cheap; wired changes are expensive. We learned this the hard way on the wizard prototypes — three rewrites because the layout shifted after the data was wired. The three DRY gates are the design-system contract from earlier in the deck (slide 21), but operationalized. "Search before you create" becomes a checklist the agent runs and announces. A screen that adds a duplicate `mc-card-v2` or inlines a hex value fails the gate before it reaches review. The catalog file inside the skill (`references/component-catalog.md`) is the inventory we built when documenting the design system. Every BEM block, every partial, every screen CSS file, with its file path. The agent reads it; you don't have to. Live demo idea: show the skill SKILL.md briefly, then show the references/component-catalog.md, then show the dry-check.md. Three files. That's the whole machine.

Slide 29b. This is the meta-point. We just showed a skill that turns a prototype into a working Studio screen. The interesting question isn't "how did you write that skill" — it's "why does it work here and not on other projects?" The answer is the harness. Before the skill exists, the design system exists. Before the design system exists, the conventions exist. Before the conventions exist, the docs exist. The skill is the *last* layer, not the first. It's the channel that points the model at everything underneath. This is the inversion of how most teams try to use AI today. The common pattern: open Cursor, prompt the model, hope it produces something coherent. Result: every output is a fresh start, every session re-derives conventions from whatever happened to be in context. The model is producing answers that are individually plausible and collectively chaos. The pattern that actually works: invest in the substrate first. Make the conventions machine-readable. Make the catalog searchable. Make the contracts checkable. Then the agent has somewhere to anchor. Then "build a Studio screen" produces something that looks like the other Studio screens — not because the model is smart, but because the substrate constrained it. Concrete examples from this project: - BEM blocks named consistently → skill can grep `.mc-*` and find every existing primitive. Without the naming convention, the catalog is impossible to build. - Tokens scoped to body.studio → skill can enumerate the legal vocabulary. Without the scope discipline, "what tokens exist?" has no honest answer. - One concern per file in src/Studio/ → skill knows where new code goes. Without it, the model picks a plausible-looking spot and the codebase fragments. - docs/studio/*.md as the source of truth → skill cites them, the human reads them, both stay in sync. Without authoritative docs, the skill becomes the source of truth and drifts from reality. The callout is the takeaway: the leverage isn't in the model. It's not in prompt engineering. It's not in picking the right framework or the right IDE. It's in the substrate the model writes against. We spent more time on the design system, the docs, and the conventions than on the skill itself — and that ratio is correct. If you take one thing from this talk: before you reach for AI to "go faster," ask whether the substrate you're pointing it at would let a *new human contributor* go faster. If the answer is no, the AI won't either — it'll just produce its incoherence at a higher rate. Fix the harness first. The agent layer is cheap once the harness is real.

Slide 30. This is the slide that addresses the elephant in the room: "what about plugin compatibility?" H5P, LTI, CAS/SAML still work at the engine layer. Post types still register. REST routes still respond. Auth still authenticates. The plugins that need Studio chrome surface have to opt in — today by being first-party (we register them), tomorrow by implementing a contract (plugins register themselves through a public hook surface). Why this posture matters: a typical WP plugin's idea of "extending the admin" is to call add_menu_page and dump its UI wherever it lands. That would destroy Studio's coherence in an afternoon. By owning the surface and closing it by default, we keep Studio looking like a product. Phase 2 will formalize this with hooks and contracts. We're deferring it deliberately — we want to see what real extension requests look like before we lock the API. Premature extensibility is harder to undo than absent extensibility.

Slide 31. One screenshot, one minute, every architectural decision visible. 1. The page header — Blade view model emits this once; reused on every screen. shapeXxxRow methods feed it. 2. The "+ Add module" toolbar — Alpine mcOrganize.addModule fires, POSTs with Accept: text/html, server returns the Blade partial, client does insertAdjacentHTML. The new card is real DOM that Alpine wires automatically. 3. The module card meta ("6 lessons · 30 sections · 18 skills · Public") — OrganizeViewModel aggregates counts server-side. No N+1, no client computation. 4. The skill chips — each chip is a Blade partial. The "+ Add skill" button hits PUT /lessons/{id}/skills with transactional semantics and structured error codes. 5. The Published toggle, License selector, Public selector — each one does a per-row current_user_can('edit_post', $lessonId) check on the server before persisting. 6. The kebab + drag handle — single aria-live region, keyboard DnD via mcKeyboardDnd, focusable button handles, full WAI-ARIA pattern. Every word in this list maps to a file you can open after the talk. If this one slide is the only thing someone remembers, they remember the right things.

Act V is the close. Three slides: what we explicitly avoided, what comes next, and the call to action.

Slide 33. Every left column is a thing we considered, tried, or saw in the prototype, then deliberately rejected. The right column is what we did instead. This isn't dogma. Each row has a specific reason it failed and a specific reason the alternative won. If a future contributor wants to bring one of these back, they need to argue against the specific reason it lost — not just "I prefer it this way." The doc trail for these decisions lives in docs/studio/ and in the commit messages. Plan files like docs/studio/OPEN-QUESTIONS.md capture things we deferred but want to revisit.

Slide 34. The near-term five are deliberately ordered. Edit-screens-on-Lexical is the next user-visible payoff — Organize lets users restructure the tree but the actual content authoring still happens in classic wp-admin. Once the edit screens land on Lexical inside Studio, the loop closes: a learner designer never leaves Studio chrome for everyday work. The Storybook is the multiplier. We shipped three BEM row blocks, the kebab menu, the page header, the topbar, the sidebar — none of them are documented as a reusable catalog. Without Storybook, every new screen re-derives "what does a card look like?" from reading organize.blade.php. With Storybook, the edit screens and any future tree screen compose from named, versioned primitives. ACL / role mapping closes a gap from this round. Today, most REST endpoints gate on edit_posts or per-post edit_post checks. That works for the happy path (administrator, editor) but doesn't honor the finer-grained roles the platform actually ships — contributor can author sections but not publish, author can publish own work but not move modules, etc. The plan is to name MC verbs (mc.module.edit, mc.lesson.reorder, mc.section.publish, mc.skills.assign…), map roles → verbs once, and replace ad-hoc checks with the named verb. This is the prerequisite for opening Studio to non-admin roles safely. Migrating admin-only settings into Studio is the corollary: once roles are honest, super admins should never have to leave Studio for routine config. Cap matrix, plugin toggles, network defaults, notification preferences — all become Studio settings screens. ?mc_studio=off remains as an escape hatch, but it should be the last resort for debugging, not the daily driver for site administration. Polishing the generator skill is the fifth leg. The pressbooks-studio-screen skill scaffolds new Studio screens from a prototype HTML file, but it was written before Organize shipped. Now that we have a canonical full-stack screen (view + view model + REST + Alpine root + BEM blocks + tests), the skill can encode those conventions directly. The next screen we generate should look like Organize without anyone having to tell it to. The medium- and long-term items are unchanged from the original plan; they remain plausible, not committed.
